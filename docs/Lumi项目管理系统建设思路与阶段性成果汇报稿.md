# Lumi 项目管理系统建设思路与阶段性成果汇报稿

> 当前版本：草案。后续先完善文稿，再据此制作 PPT 和 PDF。

## 一、为什么要做这套系统

这次开发的目标，不是简单地把 Excel 搬到网页上，也不是增加一套新的填表工作，而是希望解决公司项目管理过程中长期存在的信息分散、责任不清、进度难以掌握和问题容易遗漏等现象。

目前公司主要依靠 Excel 进行项目管理。同一个项目，在销售助理和负责所有项目进度总抓的罗琳处，分别存在两套项目资料。两套资料都在维护项目，但由于维护时间、记录方式和关注重点不同，项目数据很容易出现重复、分叉和不一致。

当管理者需要了解一个项目的真实进展时，往往还需要进一步询问相关人员、核对不同表格，甚至依靠个人记忆来判断项目目前处于什么状态。这种方式在项目数量较少时尚可维持，但当项目增多、参与人员增多、项目周期变长以后，管理成本会明显上升。

因此，我希望建立一套统一的项目管理入口，让一个项目只有一个相对明确的事实来源，所有角色围绕同一份项目数据进行协作。

## 二、目前项目管理中的三个结构性问题

### 1. 同一个项目存在多套存储，缺少统一事实来源

销售助理和项目进度总抓人员分别维护项目资料，本质上说明公司目前缺少统一的项目主记录。

这不仅会造成重复工作，也会带来几个问题：

- 同一个项目在不同表格中的进度可能不一致；
- 项目更新依赖具体人员，人员不在时信息难以及时获取；
- 管理者无法快速判断哪一份数据是最新的；
- 项目数据无法自然沉淀为长期可查询的历史资料。

问题不在于 Excel 本身，而在于项目数据没有形成统一、持续更新的管理对象。

### 2. 项目事件散落在微信群、私聊和口头沟通中

项目推进过程中，很多重要信息并不在表格里，而是存在于微信群、私聊、电话和临时沟通中。

这些信息可能包括：

- 现场出现了什么问题；
- 谁承诺在什么时间完成；
- 某个阶段为什么延期；
- 哪些资料还没有补齐；
- 客户提出了什么临时要求；
- 哪些问题需要销售、技术和生产共同协调。

当这些信息没有被结构化记录时，项目总抓就容易出现遗漏。管理人员在汇总项目时，需要依赖聊天记录、个人记忆和反复询问。时间一长，原本的小问题可能因为没有被持续跟进，逐渐拖成影响交期的大问题。

因此，项目管理不能只记录“项目当前进度”，还需要记录项目推进过程中发生的关键事件、责任人和下一步动作。

### 3. 各角色缺少真正支持工作的看板

项目链上的不同角色，目前没有一个能够真正支持工作安排的岗位看板。

销售、项目经理、技术主管、设计人员、生产人员和售后人员，关注的内容并不相同。如果所有人都面对同一张复杂表格，往往会出现两个问题：

第一，人员无法快速看到自己真正需要处理的事情。

第二，容易遗忘阶段性的动作。例如，某个项目已经进入生产，但还没有明确负责人；设计完成后缺少技术协议；设备已经发货，但尾款节点没有被持续跟踪；调机阶段出现问题后，没有明确的整改负责人。

这种遗忘并不一定是个人责任，而是因为系统没有把责任、状态、时间和提醒固定下来。

尤其是项目时间节点没有形成统一的预警机制时，项目中的所有角色都很难在同一个看板里明确当前工作的轻重缓急，也很难及时发现哪些事项已经遗漏、哪些阶段即将影响后续交付。

当问题没有被提前识别，工作就容易变成“谁更着急、谁催得更厉害，谁的问题先处理”。这种按声音和紧急程度被动分配问题的方式，会进一步放大销售与技术部门之间围绕交期、人员和资源的博弈。

如果双方没有共同认可的项目状态、优先级和阶段信息，资源协调就很难高效展开，也难以达到相对合理的平衡。

## 三、我对这个管理问题的判断

我认为，公司当前需要解决的不是“有没有一张更大的表”，而是需要建立一套围绕项目主线的管理机制。

这套机制至少要回答五个问题：

1. 这个项目当前处于什么阶段？
2. 当前阶段由谁负责？
3. 项目是否按计划推进？
4. 下一步需要谁做什么？
5. 哪些风险已经出现，哪些问题需要提前协调？

基于这个判断，我把系统设计成四个基本层次：

- 项目：所有信息围绕项目归集；
- 阶段：项目按照实际业务链条推进；
- 角色：不同岗位从自己的责任边界进入系统；
- 状态：通过状态、日期、负责人和提醒反映项目变化。

## 四、系统的核心设计思路

### 1. 一个项目，一份主记录

系统以项目为核心，将项目编号、客户、设备、合同、交期、收款、团队和阶段信息集中在一起。

项目不再只是 Excel 中的一行数据，而是一个可以持续更新、被多个角色共同使用的管理对象。

### 2. 用阶段管理项目推进

当前系统围绕生产项目建立了四个核心阶段：

> 机械设计 → 生产 → 调机 → 尾款

每个阶段都对应状态、负责人、日期和相关操作。

这样，管理者不需要只看一个笼统的“项目进度”，而是可以判断项目具体卡在哪个阶段、由谁负责，以及下一步应该推动什么。

### 3. 用角色看板支持不同岗位安排工作

系统不是让所有人看到完全相同的信息，而是根据角色提供不同的工作入口。

- 主管关注预警、缺少分配和阶段整体情况；
- 执行人员关注自己负责的项目和工序；
- 销售关注项目建立、客户和收款进度；
- 项目经理关注项目整体推进；
- 售后关注已经进入后段的项目；
- 管理员关注全局项目、人员和客户；
- 软件等协作角色可以进行跨阶段查看。

角色看板的意义，不只是权限控制，而是让每个人打开系统后，能够直接看到与自己有关的工作。

### 4. 用时间节点预警明确轻重缓急

时间节点预警是系统中非常重要的管理能力。系统根据阶段计划时间、预计交期和实际完成情况，将项目和工序区分为正常、预警、逾期或已完成等状态，并在不同角色的工作台中突出需要关注的项目。

这样，项目中的每个角色都可以在看板中明确：

- 当前最紧急的工作是什么；
- 哪些工作已经接近时间节点；
- 哪些项目已经逾期或存在延期风险；
- 哪些阶段还没有负责人或下一步动作；
- 哪些遗漏项可能影响后续阶段和整体交付。

这使看板从“项目列表”变成了“工作优先级和遗漏项的提醒入口”。它不替代人员判断，但为所有角色提供同一套时间依据，减少依靠催促和记忆进行安排的情况。

### 5. 用项目卡片实现快速判断

项目卡片是系统中最频繁使用的管理单元。

卡片集中展示：

- 项目编号；
- 项目经理和销售人员；
- 各阶段当前状态；
- 各阶段负责人；
- 交期和剩余时间；
- 项目预警；
- 收款进度和尾款状态。

管理者可以先通过卡片快速判断项目是否正常，再进入项目主页进一步处理。

### 6. 用项目主页承载完整上下文

项目主页用于处理更完整的项目信息，包括：

- 项目基本信息和设备清单；
- 合同周期和预计交期；
- 项目团队及人员分配；
- 阶段进度；
- 整改工序和现场事件；
- 技术协议；
- 收款进度；
- 项目当前需要处理的动作。

项目卡片负责“快速看”，项目主页负责“深入管”。这样可以减少信息在多个表格、聊天窗口和人员记忆之间来回切换。

## 五、目前已经完成的工作

目前系统已经完成了从界面到业务规则的整体落地，主要包括：

- 7 类角色工作台；
- 11 个角色定义；
- 机械设计、生产、调机、尾款四个核心阶段；
- 项目卡片和项目主页；
- 项目阶段状态管理；
- 负责人分配和阶段权限；
- 项目计划时间、交期和逾期判断；
- 面向不同角色的时间节点预警和轻重缓急提示；
- 收款进度和尾款提醒；
- 技术协议上传；
- 整改工序和现场事件记录；
- Excel 数据导入；
- 前后端测试；
- 一键构建和程序打包部署。

从当前代码规模看，系统包含 26 个后端 Python 文件、36 个前端 TypeScript/TSX 文件和 7 个测试文件。

但我认为，工作量不能只用代码数量来衡量。更重要的是，我把公司实际项目推进中的阶段关系、角色责任、进度判断、尾款节点和资源协调问题，逐步转化成了系统中的数据结构和操作规则。

## 六、项目工作量与时间投入说明

这套系统不是单个页面的制作，而是一项从管理问题梳理到系统交付的完整工作，涉及需求分析、数据模型、后端接口、前端页面、角色权限、阶段规则、测试、数据导入和程序打包等多个层面。

从功能和工程规模看，本项目已经完成了：

- 7 类角色工作台和 11 个角色定义；
- 4 个核心项目阶段及其状态规则；
- 项目卡片、项目主页、负责人分配、预警和收款管理；
- 前后端联调、测试、Excel 数据导入和一键构建交付。

同时需要说明，本项目是在不影响本职工作的前提下推进的，并没有脱离岗位另起炉灶。开发主要利用正常工作中的零散时间、任务间隙以及个人时间完成，正常工作时间内专门用于本项目的投入是有限的。

因此，这项工作应当被理解为：在实际工作中发现项目管理问题，并利用有限时间为公司设计和实现解决方案，而不是脱离日常职责进行的个人副业。

## 七、这套系统希望带来的管理变化

这套系统并不是要替代管理人员，也不是要让所有管理动作都自动完成，而是希望带来几个基础变化：

第一，让项目状态从“需要询问”变成“可以直接查看”。

第二，让项目责任从“大家都知道”变成“系统中有明确分配”。

第三，让问题从“出了问题再处理”变成“在阶段中提前暴露”。

第四，让所有角色能够通过时间节点预警判断当前工作的轻重缓急和遗漏项，而不是只依靠催促、经验和个人记忆安排工作。

第五，让销售和技术之间的资源协调，有共同的项目状态和时间依据作为基础，而不是只依靠临时沟通。

第六，让项目推进过程中产生的信息逐渐沉淀下来，不再完全依赖某个人的记忆和聊天记录。

目前，这套系统更像是公司项目管理的基础设施。它首先要解决的是信息统一、责任明确和状态可见，后续再基于实际使用情况，继续完善提醒、统计、历史分析和跨项目资源分析能力。

## 八、统一项目数据库带来的数据分析与挖掘能力

当项目、阶段、人员、事件、时间、收款和问题处理记录持续沉淀在统一数据库中，系统的价值就不只体现在查看单个项目，还可以进一步服务于企业管理、过程分析和管理决策。

### 1. 任意筛选和分组项目

管理人员可以按照项目状态、当前阶段、负责人、客户、交期、预警等级、收款情况等条件筛选项目，并进行分组查看。

这样可以快速回答诸如“哪些项目即将逾期”“哪些项目还没有明确负责人”“哪些项目已经进入尾款阶段”“某个负责人当前承担了哪些项目”等问题，减少人工翻表和重复汇总。

### 2. 汇总项目事件日志，查找管理短板

项目中的延期原因、整改事项、现场问题、资料缺失和状态变更，都可以按照阶段、项目、责任角色和问题类型进行汇总。

通过分析这些事件的发生频率、持续时间和重复原因，可以发现项目链条中的短板。例如，某一阶段经常等待资料，某一类设备反复出现相同问题，某个环节经常发生责任交接不清等。这样，管理改进就可以从个别项目的经验判断，逐步转向基于数据的集中改进。

### 3. 便于管理层直接跟踪项目进度

管理层可以直接查看项目总量、正常项目、预警项目、逾期项目、阶段分布、未分配项目和尾款风险，而不必每次等待人工整理汇报。

管理层看到的不只是某个人汇总后的结果，还可以根据需要下钻到具体项目、具体阶段和具体事件，了解问题产生的过程。

### 4. 支持人员负荷和资源安排

通过汇总不同阶段的项目数量、时间节点和负责人分配情况，可以观察设计、生产、调机等岗位的任务负荷和即将到来的工作高峰。

这为销售与技术部门之间围绕交期、人力和优先级的协调提供共同依据，使资源讨论从“哪个项目更着急”逐步转向“当前资源在哪里、项目节点是什么、怎样安排更合理”。

### 5. 沉淀历史规律，优化流程和计划

长期积累后，可以比较不同项目的实际周期、延期原因、阶段耗时和重复问题，为后续的交期评估、人员培养、工序模板优化和风险预判提供依据。

需要说明的是，统一数据库并不意味着数据会自动产生价值。上述分析能力建立在项目数据持续更新、事件记录规范、状态口径统一的基础上。因此，系统建设不仅是软件开发，也包括逐步建立配套的数据管理习惯。

## 九、下一步规划

下一阶段，我认为最重要的不是继续增加大量功能，而是让系统真正进入日常使用，并形成稳定的更新规则。

后续可以重点推进：

- 明确不同角色什么时候必须更新项目；
- 明确项目阶段状态的统一口径；
- 选择一批真实项目进行试运行；
- 统计项目延期、缺失分配和尾款预警情况；
- 根据使用反馈完善提醒和数据分析；
- 逐步沉淀项目历史，为后续管理决策提供依据。

## 十、后续汇报文稿与 PDF 编排指导

后续制作汇报文稿、PPT 和 PDF 时，应当遵循“先问题、后方案；先事实、后功能；用真实截图具象化设计思路”的顺序。

汇报材料不应一开始就罗列系统页面和技术功能，而应先让领导理解：公司当前的项目管理为什么容易遗漏、为什么容易拖延，以及为什么销售和技术之间的资源协调缺少共同依据。

建议采用以下页面结构：

1. **封面与一句话结论**：说明这套系统要解决的是项目状态不统一、责任不清和风险发现滞后的问题。
2. **当前管理现状**：首先呈现 Excel 多头存储、微信信息散落、角色缺少工作看板三个结构性问题。
3. **五个管理问题**：明确提出“项目现在处于什么阶段、谁负责、是否按计划、下一步做什么、风险如何协调”五个问题。
4. **系统回应页面**：每个问题至少对应一张系统真实截图，并在截图旁说明系统如何回答这个问题。
5. **工作量与时间投入**：说明系统涉及的工作范围、已完成的工程量，以及本项目只占用了很少的正常工作时间。
6. **价值、边界与下一步**：区分当前已经实现的能力和未来规划，避免把设想中的功能表述为已经落地的成果。

五个问题与截图的对应关系建议如下：

| 管理问题 | 建议使用的实际截图 | 截图中需要标注的内容 | 对问题的回应 |
| --- | --- | --- | --- |
| 项目当前处于什么阶段？ | 项目卡片、项目主页的阶段进度 | 阶段名称、当前状态、完成日期、预计交期 | 把项目从一个订单编号转化为可追踪的阶段链 |
| 当前阶段由谁负责？ | 项目主页的项目团队、主管工作台 | 角色、责任人、缺失分配提示 | 把“大家都知道”变成明确的责任分配 |
| 项目是否按计划推进？ | 项目卡片、角色工作台的预警分组、项目主页日期区域 | 交期、剩余天数、预警、逾期状态、遗漏分配 | 通过时间节点提前识别拖延，并明确轻重缓急 |
| 下一步需要谁做什么？ | 执行人工作台、阶段状态操作区域 | 我的项目、我的阶段、可执行操作 | 让每个角色打开系统就能看到自己的工作 |
| 风险如何被发现和协调？ | 主管工作台、整改事件、技术协议和尾款区域 | 缺失分配、整改、协议、尾款提醒 | 为销售、技术和管理者提供共同的项目事实 |

截图使用还应遵循以下原则：

- 优先使用系统真实运行截图，不使用抽象示意图代替核心证据；
- 尽量使用同一个示例项目贯穿多页，让领导看到同一项目如何被不同角色使用；
- 每张截图只标注一到三个关键区域，避免缩小整页后无法阅读；
- 时间节点预警截图应明确展示正常、预警、逾期和遗漏分配等状态，让领导能直接看出看板如何帮助角色安排轻重缓急；
- 截图中的客户、订单、人员等敏感信息应根据需要脱敏；
- 每张截图都要配一句“这张图回答了什么问题”，不能只展示页面名称；
- 如果某项功能尚未实现，应明确标注为“后续规划”，不能与已实现功能混在一起；
- 不要在开头展示技术栈、代码结构或大量功能清单，技术细节放在附录即可。

最终的 PDF 应当让领导在没有现场讲解的情况下，沿着下面的逻辑读完：

> 公司目前遇到什么问题 → 这些问题为什么会发生 → 系统如何逐一回应 → 我完成了哪些工作 → 这套系统下一步能带来什么管理价值。

## 十一、结语

我希望这套系统最终解决的，不只是“项目资料放在哪里”的问题，而是让公司形成一套更清晰的项目推进语言：

项目当前在哪里，谁负责，下一步做什么，是否存在风险，资源应该如何安排。

这套系统的价值，不在于增加了一套软件，而在于把原本分散在 Excel、聊天记录和个人记忆中的项目管理经验，逐步沉淀成一套可以被共同使用、持续更新和不断改进的管理机制。
