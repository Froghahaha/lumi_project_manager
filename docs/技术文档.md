## 1. 系统概述

Lumi 是一套面向生产型企业的项目管理系统，核心管理对象是"项目—工序—人员—收款"四要素。

### 1.1 核心概念

| 概念 | 说明 |
|------|------|
| **项目 (Project)** | 一个设备订单，包含客户信息、合同条款、设备清单、团队分配 |
| **工序 (Phase)** | 项目流转的基本单元：机械设计 → 生产 → 调机 → 验收 → 尾款，可存在多个同序工序 |
| **人员 (Person)** | 系统用户，可拥有多个角色（多对多） |
| **角色 (Role)** | 定义人员职能、权限、归属工作区 |
| **工作区 (Workspace)** | 按角色划分的页面视图，不同角色看到不同内容 |
| **授权 (Authorization)** | 基于 Oso Polar 策略的 RBAC 权限系统 |
| **工序生命周期 (Phase Lifecycle)** | 集中管理工序状态流转、自动触发尾款、进度计算的统一模块 |

### 1.2 技术栈

| 层 | 技术 | 版本 |
|----|------|------|
| 后端框架 | FastAPI | 0.115 |
| 数据库 ORM | SQLModel (基于 SQLAlchemy) | 0.0.24 |
| 数据库 | SQLite | 内置 |
| 授权引擎 | Oso (Polar 策略语言) | 最新 |
| 前端框架 | React | 19 |
| 前端 UI | Ant Design | 6 |
| 路由 | React Router | 7 |
| 构建工具 | Vite | 8 |
| 桌面打包 | PyInstaller | 6.20 |
| 测试 | pytest / Vitest | |

### 2.2 数据流

```
用户操作 → React Router → Loader (获取数据) → Page 渲染
  ↓                          ↑
  Component 交互 → API Call → REST Endpoint → Router Handler
                                                ↓
                              Depends(认证检查) → DB Query → Serialize → Response
                                                ↓
                              compute_phase_progress() / compute_project_status()
                              phase_lifecycle.apply_terminal_side_effect()
```

### 2.3 路由注册顺序

FastAPI 路由和挂载的注册顺序直接影响请求分发：

```python
# main.py 中的注册顺序
1. include_router(customers)  →  /customers
2. include_router(projects)   →  /projects
3. include_router(persons)    →  /persons
4. include_router(misc)       →  /roles, /phases, /templates, /incidents, /assignments
5. include_router(auth)       →  /login, /me/permissions
6. mount("/assets", ...)      →  静态资源
7. mount("/", SPAStaticFiles) →  SPA 回退（所有非 API 路径返回 index.html）
```

**关键规则**: API 路由优先于静态文件挂载。`_SPAStaticFiles` 自定义类在文件未找到时回退到 `index.html`，确保 React Router 客户端路由正常工作。

## 3. 后端模块

### 3.1 入口 (`main.py`)

职责: 创建 FastAPI 应用，注册中间件、路由、静态文件挂载、启动事件。

设计要点:
- CORS 全开（开发模式），生产部署应限制 `allow_origins`
- 静态文件通过 `_SPAStaticFiles` 挂载，支持 SPA 路由回退
- `startup` 事件调用 `init_db()` 执行 Schema 迁移和种子数据

### 3.2 数据库层 (`db.py`)

职责: SQLite 引擎创建、Schema 迁移、会话管理。

迁移策略为三段式:
1. **预迁移**: 在旧表删除前迁移数据（如 `person_role` → `person.role_code`）
2. **Schema 重建**: `SQLModel.metadata.create_all()` 创建/保留当前表
3. **后迁移**: 对已有表执行 `ALTER TABLE ADD COLUMN` 添加新字段

关键常量:
```python
DB_PATH = Path(sys.executable).parent / 'data.db'  # PyInstaller 模式下
DB_PATH = Path(__file__).resolve().parents[2] / 'data.db'  # 开发模式下
PRODUCTION_TEMPLATE_ID = uuid.uuid5(uuid.NAMESPACE_DNS, "template.production")
```

### 3.3 ORM 模型 (`models.py`)

11 个 SQLModel 表，无外键关系约束（SQLite 兼容），通过 `Field(foreign_key=...)` 声明逻辑外键。

模型关系图:
```
Customer ──1:N── Project ──1:N── ProjectPhase ──1:N── PhaseIncident
                      │              │
                      │              └── 可选: 绑定到工序的人员分配
                      │
                      ├──1:N── ProjectAssignment (人员分配, 可选绑定 phase)
                      │
                      ├──1:N── ProjectEquipment (设备清单)
                      │
                      └──N:1── PhaseTemplate ──1:N── PhaseTemplateItem

Person ──N:M── RoleDefinition (通过 PersonRole 桥接表)
```

**关键字段说明**:

| 模型 | 字段 | 说明 |
|------|------|------|
| `Project` | `payment_due_type` | 尾款到期条件: `after_tuning` / `after_shipping` / `after_acceptance` |
| `Project` | `payment_due_days` | 尾款到期天数 N |
| `Project` | `contract_payment_progress` | 实际收款进度 0.0 ~ 1.0 |
| `Project` | `contract_effective_date` | 项目生效日期（收款达标后自动写入） |
| `ProjectPhase` | `seq` | 工序类型标识（1-5），非唯一——同一项目可有多个 seq=2 的工序 |
| `ProjectPhase` | `is_rectify` | 整改标记，整改工序可任意 seq |
| `ProjectPhase` | `sub_statuses_json` | 可选状态列表，从模板反范式化复制 |
| `ProjectPhase` | `terminal_statuses_json` | 终态列表，匹配任一即视为工序完成 |
| `RoleDefinition` | `assigns_json` | 该角色可指派的角色代码 JSON 数组 |
| `ProjectAssignment` | `phase_id` | 可选，关联到具体工序(全局分配为 null) |

### 3.4 Pydantic Schema (`schemas.py`)

分层设计：`Create` 用于请求体，`Out` 用于响应体。`ProjectOut` 和 `ProjectPhaseOut` 包含后端计算字段:

```python
class ProjectOut(BaseModel):
    ...
    project_status: str = ""    # 正常|逾期|已完成 — 由 compute_project_status() 计算
    payment_due_date: str | None = None  # 由 compute_payment_due_date() 计算

class ProjectPhaseOut(BaseModel):
    ...
    phase_progress: str = ""    # 未开始|进行中|预警|逾期|已完成 — 由 compute_phase_progress() 计算
```

### 3.5 路由层 (`routers/`)

5 个路由模块，按领域职责拆分:

| 路由模块 | 前缀 | 主要端点 | 权限要求 |
|---------|------|---------|---------|
| `auth.py` | 无 | `POST /login`, `GET /me/permissions` | 公开 / 登录 |
| `projects.py` | `/projects` | 项目 CRUD, 工序 CRUD, 分配 CRUD, 协议上传 | 按操作 |
| `customers.py` | `/customers` | 客户 CRUD | 管理员/销售助理 |
| `persons.py` | `/persons` | 人员 CRUD, 状态开关, 密码重置 | 管理员 |
| `misc.py` | 无 | 模板/角色/全局工序/事故事件 | 按操作 |

**权限检查模式**:
```python
# 方式 1: require_permission 依赖注入 (API 级)
def update_project(body, actor=Depends(require_permission("projects:edit", "project"))):

# 方式 2: deny_salesman 依赖注入 (屏蔽销售写操作)
def add_phase(body, actor=Depends(deny_salesman)):

# 方式 3: 手动 phase_lifecycle 检查 (工序级)
if not can_manage_phase(actor.roles, ph.seq):
    raise HTTPException(403, "权限不足")
```

### 3.8 授权引擎 (`authz.py` + `authorization.polar`)

基于 Oso 框架的 RBAC。Polar 策略文件定义 `allow` 规则，Python 端注册 `AppUser` 并调用策略检查。

```python
PERMISSION_RESOURCE = {
    "projects:create": "project",      # API 权限
    "view_payment_column": "ui",       # UI 权限
    "phase_responsibility:1": "ui",    # 工作区配置
}
```

### 3.9 依赖注入 (`deps.py`)

提供 FastAPI 依赖:

| 依赖 | 用途 |
|------|------|
| `get_session()` | 提供数据库 Session（上下文管理器，自动提交/回滚） |
| `get_current_user()` | 解析 Bearer Token，返回 `AppUser` |
| `require_permission(action, resource)` | 权限检查工厂 |
| `deny_salesman()` | 阻止销售角色写操作 |

Token 存储于内存字典，24 小时过期，支持自动清理。

### 3.10 种子数据 (`seed.py`)

| 函数 | 职责 | 幂等性 |
|------|------|--------|
| `seed_default_template()` | 创建 5 阶段模板并同步 TTL（覆盖写入） | 是（删除旧项重新创建） |
| `seed_role_definitions()` | 写入 11 个角色定义 | 是（检查已存在则跳过） |
| `seed_persons()` | 写入 4 个默认用户 | 是（检查有人则跳过） |
| `migrate_person_role()` | 迁移旧版 role_code 到多对多表 | 是（检查有数据则跳过） |

### 3.11 事故事件管理 (`misc.py` 中 incident 路由)

事故事件 (`PhaseIncident`) 是绑定到工序的日志型记录，用于记录"现状描述"和"逾期原因"。

权限规则:
- 管理员/主管: 可添加任何工序的事故事件
- 工序执行人: 可添加自己工序的事故事件
- 项目成员: 可在整改工序添加事故事件
- 销售: 仅可在尾款工序添加事故事件

## 4. 前端模块

### 4.1 路由 (`router.tsx`)

基于 React Router v7 的 `createBrowserRouter`，路由结构:

```
/login          → LoginPage (公开)
/               → 根据登录状态重定向到 /workspace 或 /login
/app (Layout)   → 需要认证
  /workspace     → WorkspacePage (按角色分发到对应工作区)
  /dashboard     → DashboardPage
  /projects      → ProjectsPage
  /projects/:id  → ProjectPage
```

Loader 模式: `/projects` 和 `/projects/:id` 使用 `loader` 预取数据，Page 组件通过 `useLoaderData()` 读取。

### 4.2 认证上下文 (`AuthContext.tsx`)

`AuthProvider` 通过 Context 向下传递认证状态:

```typescript
type AuthState = {
  person: Person | null     // 当前登录人员
  token: string             // Bearer Token
  role: string              // 当前选中角色代码
  roleName: string          // 当前选中角色名称
  can: Record<string, bool> // 权限位图（从 /me/permissions 获取）
  login, logout, setRole,
  hasPermission, refreshPermissions
}
```

**状态持久化**: `localStorage('lumi_auth')` 保存 person/token/role/roleName。

**权限刷新时机**: 组件挂载时 + 角色切换时 → 调用 `GET /me/permissions` 获取 27 个权限布尔值。

### 4.4 类型系统 (`types.ts`)

使用品牌类型 (Branded Type) 防止误用:

```typescript
declare const PhaseIdBrand: unique symbol
export type PhaseId = string & { [PhaseIdBrand]: true }
export const asPhaseId = (s: string): PhaseId => s as PhaseId
```

这确保 `seq` (number) 和 `phase_name` (string) 不会被误传给需要 `phase_id` 的参数。

### 4.7 紧急度分组 (`utils/urgency.ts`)

每个分组下有 `warn`（预警）和 `overdue`（逾期）两个级别。

### 5.2 反范式化说明

`project_phase.sub_statuses_json` 和 `terminal_statuses_json` 是从 `phase_template_item` 反范式化复制到每个工序的。这样设计的理由:

1. **历史一致性**: 模板更改后，存量项目仍保有创建时的状态配置
2. **查询性能**: 不用 JOIN 模板表即可获取可选状态
3. **灵活覆盖**: 单个工序可独立修改状态配置（如整改工序）

同步策略: `seed_default_template()` 在启动时自动同步存量项目阶段（仅当配置变更时）。

### 5.3 数据库迁移

无迁移框架(Alembic)，通过 `init_db()` 自动管理。变更 Schema 的步骤:

1. 在 `models.py` 中添加新字段
2. 在 `db.py` 的 `init_db()` 后迁移阶段添加 `ALTER TABLE ADD COLUMN`
3. 重启应用 → 自动迁移

安全机制:
- `CREATE TABLE IF NOT EXISTS` + `SQLModel.metadata.create_all()` 保证幂等
- `ALTER TABLE` 前先 `inspect` 检查列是否存在
- 旧表自动删除（`SQLModel.metadata` 之外的表视为过期）

### 6.3 双层校验

| 层 | 机制 | 用途 |
|----|------|------|

### 6.4 工序级权限

除 Polar 策略外，`phase_lifecycle.py` 实现了工序级别的权限控制:

```python
SUPERVISOR_MANAGED = {
    'tech_supervisor': [1, 2],      # 技术主管管理: 机械设计、生产
    'after_sales_super': [3, 4, 5], # 售后主管管理: 调机、验收、尾款
}

def can_manage_phase(roles: list[str], seq: int) -> bool:
    if 'admin' in roles: return True
    for role, seqs in SUPERVISOR_MANAGED.items():
        if role in roles and seq in seqs: return True
    return False
```

### 6.5 销售角色限制

销售 (`salesman`) 有特殊的限制:
- 不能通过 `deny_salesman` 依赖的写操作（创建/编辑/删除项目、工序、分配）
- 仅可在自己分配的尾款工序上添加事故事件
- 有收款进度查看和编辑权限（UI 层面）

### 7.4 状态流转

标准 5 工序及其状态:

| seq | 工序 | 可选状态 | 终态 |
|-----|------|---------|------|
| 1 | 机械设计 | 未开始, 设计中, 图纸已下发 | 图纸已下发 |
| 2 | 生产 | 未开始, 生产中, 生产完成, 已发货 | 已发货 |
| 3 | 调机 | 未开始, 安调中, 安调完成 | 安调完成 |
| 4 | 验收 | 未开始, 已验收 | 已验收 |
| 5 | 尾款 | 收款中, 收款完成 | 收款完成 |

进度判定顺序:
```
terminal_statuses 匹配 → 已完成
actual_end_date 不为空  → 已完成
today > planned_end     → 逾期
today >= warning_date   → 预警
status 不为空           → 进行中
默认                    → 未开始
```

### 7.5 尾款自动触发

当某个工序达到终态且满足 `payment_due_type` 配置时，自动激活尾款工序：

```python
TAIL_TRIGGER = {
    'after_tuning': 3,      # 调机完成 → 触发尾款
    'after_shipping': 2,    # 已发货 → 触发尾款
    'after_acceptance': 4,  # 验收完成 → 触发尾款
}
```

触发逻辑 (`_activate_tail`):
1. 尾款工序尚未开始（`start_date` 为空）
2. 设置 `start_date = today`
3. 如有 `payment_due_days`，计算 `planned_end_date`
4. 设置 `status = '进行中'`

### 7.6 全量收款自动生效

在 `PATCH /projects/{id}` 中，当 `contract_payment_progress >= contract_deposit_ratio` 且 `contract_effective_date` 未设置时:

1. 设置 `contract_effective_date = today`
2. 如有 `contract_duration_days`，计算 `contract_expected_delivery_date`

## 10. 治理思想

### 10.1 集中配置 (Centralized Configuration)

**原则**: 任何领域常量、状态定义、权限规则，有且仅有一个定义位置。

| 配置项 | 单一来源 | 使用方 |
|--------|---------|--------|
| 工序定义 (名称、序号、状态) | `backend/seed.py` → DB | 全系统 |
| 工序状态校验 | `phase_lifecycle.py` | 后端 API |
| 工序常量 | `frontend/utils/phaseConfig.ts` | 前端组件 |
| 权限规则 | `authorization.polar` | 后端 + 前端 |
| 角色定义 | `seed.py` → DB | 全系统 |

**禁止**: 在任何组件/路由中硬编码工序序号、角色代码、状态字符串。

### 10.2 单一职责 (Single Responsibility)

每个模块只做一件事:

| 模块 | 职责 | 不应包含 |
|------|------|---------|
| `utils_compute.py` | 状态计算 | DB 查询、HTTP 处理 |
| `utils_serialize.py` | ORM→Schema 转换 | 业务逻辑、计算 |
| `phase_lifecycle.py` | 工序生命周期 | 项目 CRUD、前端渲染 |
| `authz.py` | 权限检查 | 用户管理、令牌生成 |
| `deps.py` | FastAPI 依赖注入 | 业务逻辑、数据库操作 |

### 10.3 抽象层 (Abstraction Layer)

引入间接层防止直接依赖具体值:

```typescript
// ❌ 不良实践: 直接依赖序号
const designPhases = project.phases.filter((ph) => ph.seq === 1)

// ✅ 良好实践: 通过访问器
const designPhases = phasesOfSeq(project, PHASE_SEQ['机械设计'])
// 或更简洁:
const designPhases = phasesOfSeq(project, 1)  // PHASE_SEQ 是常量，不改变
```

### 10.4 反范式化权衡 (Denormalization Trade-offs)

系统在某些场景有意识地使用了反范式化:

| 场景 | 反范式化内容 | 理由 |
|------|-------------|------|
| 工序可选状态 | `sub_statuses_json` 在 `project_phase` | 历史一致 + 避免 JOIN |
| 角色可指派列表 | `assigns_json` 在 `role_definition` | 单表读取，权限检查高频 |
| 权限位图 | `can` 对象在前端 `AuthContext` | 避免每次 UI 渲染都调用 API |

核心准则: **读取频繁、写入低频、一致性要求不高的数据可以反范式化**。

### 10.5 服务层治理 (Service Layer Governance)

本系统没有传统的 service 层，而是采用分层架构:

```
Route Handler → Depends (认证/权限) → DB Query → Compute → Serialize → Response
```

这种"薄路由 + 厚工具函数"的架构在设计上有意为之:
- 避免过度抽象（引入 service 层需要管理依赖、生命周期）
- 保持代码扁平，容易追踪数据流
- 纯函数 (`utils_compute.py`) 比 service 对象更容易测试

**何时应该引入 service 层**: 当出现以下情况时，应提取 service:
1. 同一个业务逻辑需要在多个 router handler 中复用
2. 业务逻辑涉及跨多个表的复杂事务
3. 测试时需要 mock service 层

### 10.6 权限边界 (Authorization Boundaries)

权限检查在三个层面执行:

```
┌─────────────────────────────────┐
│ 第1层: UI 隐藏 (前端)            │
│ hasPermission('projects:create') │
│ → 隐藏"新建项目"按钮             │
├─────────────────────────────────┤
│ 第2层: API 注入 (后端路由)       │
│ require_permission()             │
│ → 拒绝未授权的 API 请求          │
├─────────────────────────────────┤
│ 第3层: 数据级检查 (后端路由)     │
│ can_manage_phase(roles, seq)     │
│ → 检查是否可管理具体工序         │
└─────────────────────────────────┘
```

UI 隐藏只是提升用户体验，真正的安全边界在后端。

## 11. 编码规约

### 11.1 TypeScript / 前端

**命名**:
- 文件: camelCase（`phaseConfig.ts`, `format.test.ts`）
- 函数: camelCase（`fmtDate`, `updatePhaseStatus`）
- 类型/接口: PascalCase（`ProjectPhase`, `PhasePerms`）
- 常量: UPPER_SNAKE（`PHASE_ORDER`, `SUPERVISOR_SEQS`）

**导入顺序**: 标准库 → 第三方库 → 组件 → 工具函数 → 类型

**组件准则**:
- 函数组件，无 class 组件
- Props 接口定义在组件同文件或就近的 types.ts
- Props 用 `type` 而非 `interface`
- 使用 `const Component = ({ ... }: Props)` 模式

**状态管理**:
- 全局状态: `AuthContext`
- 页面数据: React Router `loader` + `useLoaderData()`
- 局部 UI 状态: `useState`
- 避免引入 Redux/Zustand（当前不需要）

**条件渲染**:
- 使用三元表达式和 `&&`，避免 `if-else return`

**禁止**:
- 在组件中硬编码工序序号/名称
- 在组件中直接 import `dayjs` 做日期计算（使用 `format.ts` 包装）
- 使用 `any` 类型

### 11.2 Python / 后端

**命名**:
- 文件: snake_case（`phase_lifecycle.py`, `utils_compute.py`）
- 函数/变量: snake_case（`compute_phase_progress`, `get_session`）
- 类: PascalCase（`ProjectPhase`, `AppUser`）
- 常量: UPPER_SNAKE（`TAIL_TRIGGER`, `WARNING_LEAD_DAYS`）

**导入顺序**: `from __future__ import annotations` → 标准库 → 第三方库 → 本地模块

**路由 Handler 模式**:
```python
@router.xxx("/path", response_model=..., status_code=...)
def handler_name(
    path_param: type,
    body: SchemaCreate | None = None,
    actor=Depends(dependency),
    session: Session = Depends(get_session),
):
    # 1. 参数校验 (Pydantic + Path params)
    # 2. 业务逻辑
    # 3. 返回 SchemaOut
```

**依赖注入原则**:
- `get_session` 所有需要 DB 访问的 handler 都需要
- `get_current_user` 需要登录的 handler 都需要
- `require_permission` 需要权限检查的 handler 使用
- `deny_salesman` 阻止销售写操作

### 11.3 数据库注意事项

SQLite 限制:
- 不支持并发写（多个连接同时写入会报错）
- 不支持 `ALTER TABLE DROP COLUMN`（旧版本 SQLite）
- 外键约束默认不启用（SQLModel 用 `foreign_key` 声明但不强制）

迁移安全:
- 添加字段必须使用 `ALTER TABLE ADD COLUMN`
- 删除字段需要先确认数据已迁移
- 删除表需要确认没有外键依赖
